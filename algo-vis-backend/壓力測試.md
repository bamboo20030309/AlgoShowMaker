# 編譯服務壓力測試

測試工具使用獨立 Cookie 模擬不同使用者，透過非同步編譯 API 排隊、輪詢並下載結果。執行前先確認：

```bash
curl -s http://127.0.0.1/api/compile/queue | jq
```

若端點不是 `200`，代表伺服器尚未部署新版編譯佇列，不應開始加壓。

## 建議順序

```bash
node scripts/compile-load-test.js --base=http://127.0.0.1 --scenario=cache --clients=50
node scripts/compile-load-test.js --base=http://127.0.0.1 --scenario=mixed --clients=50 --ramp-seconds=60
node scripts/compile-load-test.js --base=http://127.0.0.1 --scenario=cold --clients=50
node scripts/compile-load-test.js --base=http://127.0.0.1 --scenario=isolation --clients=20
node scripts/compile-load-test.js --base=http://127.0.0.1 --scenario=limits --clients=4
```

- `cache`：相同程式、不同輸入，驗證執行檔快取及個別 Trace。
- `mixed`：每五人一份新程式，其餘使用共用程式，模擬展示流量。
- `cold`：每人提交不同程式，測量最昂貴的全新編譯尖峰。
- `isolation`：每人產生不同編譯錯誤，確認錯誤與 debug 訊息不互相混入。
- `limits`：依序驗證正常、TLE、OLE、MLE；MLE 必須在 Linux Docker 執行，Windows 開發服務沒有 `ulimit`。

測試輸出包含 P50／P95／最大延遲、最高排隊位置、佇列尖峰、判定統計及最後狀態。成功測試結束時，正式佇列與非同步佇列都必須回到零。

測試期間另開終端監控：

```bash
watch -n 1 'curl -s http://127.0.0.1/api/compile/queue | jq'
docker stats
```

第一行每秒顯示佇列、worker 與快取；第二行持續顯示各容器的 CPU、記憶體及 PIDs。按 `Ctrl+C` 只會停止監看，不會停止服務。
